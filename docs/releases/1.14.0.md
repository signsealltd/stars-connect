# STARS Connect V1.14.0 — Safety & Compliance

Previous release: V1.13.1. This is one feature-release increment; package.json remains the version source.

## Delivered workflows

- `/dashboard/premises` is the live Safety & Compliance hub. Policies, RAMS Studio, Asset Management and Tests & Inspections are primary cards; actions, insurance/documents, COSHH/RIDDOR and the existing Fleet workflows remain connected. Empty libraries are not shown as compliant. No production sample records are seeded.
- `/dashboard/premises/policies` and `/coshh` provide controlled drafts, owners, reviewers/approvers, dates, relevant staff groups, attachments, review, changes requested, approval, publication, revisions and retained history. Uploaded document replacements retain earlier files and expose version links.
- `/dashboard/premises/rams` replaces the pilot entry. `/dashboard/health-safety` redirects there. Existing record IDs, hazards, method steps, approvals and files are reused; no RAMS data is copied into a second system. Draft duplication, revision, historical PDFs, photographs/documents and archive history are available. Published and approved versions cannot be edited in place.
- `/staff/policies` and the Training area show only applicable published controlled versions. Publication sends a version-specific notification. Staff acknowledgements retain exact version, statement version, time and session/request context; new published versions need new receipts. `/dashboard/premises/reports` reports acknowledgement coverage by document and staff member.
- Assets have stable random QR tokens, authenticated `/dashboard/premises/assets/[token]` pages and printable STARS labels. Metadata includes reference, status, supplier, warranty, service dates, checklist template, photograph link, related records and decommissioning reason. Existing documents provide uploaded photograph/file storage. Service notes and changes are audited.
- Asset inspections support checklist outcomes, pass/fail/not applicable, evidence links, certificate references and recurrence from the asset interval. Failures create linked actions; failed safety checks stop asset use. Required evidence and a different authorised verifier protect completion. Original inspection changes retain audit history.
- Task owners can be changed using an active staff selector and a confirmation preview. Assignee notifications and `/staff/tasks` reflect the change. Review/approval permissions are not granted by ownership. Ordinary task title, note and due-date proposals use an old/new preview and reject stale saves.
- Fleet has an Archived vehicles view for archived and previously soft-deleted records. Restore puts the vehicle out of service for verification. Permanent deletion is restricted to archived vehicles with no checks, defects, maintenance or documents; historical records and audit trails are retained.

## Clive

Clive for Compliance uses the existing avatar with readable white text. Live task queries apply the user's source permissions, dates and statuses. Examples: “What is overdue?”, “What is awaiting evidence?”, “What does Kellie own?” and “What must we prepare for Monday’s review?”. Results link to real records. Published policy/RAMS and asset searches do not fabricate missing library content.

Owner changes, draft task creation and title/date/note edits require confirmation in the UI. Ambiguous matches require selection. Accepted RAMS suggestions have an audit record and remain draft content. Clive cannot approve or publish safety documents, certify compliance, approve HR requests, change medication instructions or independently complete safety work. Registered help targets support temporary highlights and reduced-motion preferences.

Source-managed safety reminders resolve from their source workflow, rather than pretending an inspection, acknowledgement or approval was performed. Medication and vehicle safety tasks retain their existing dedicated workflows. Staff-request reviewers remain separate from ordinary task ownership.

## Reminders and permissions

Safety reminders use stable source/version/date keys to prevent duplication. The Tasks read refresh reconciles safety reminders for authorised compliance users; the existing authenticated daily report job also invokes the same reconciliation. `/api/cron/safety-reminders` is an optional independent POST endpoint using `REPORT_JOB_SECRET`. Existing daily-job installations need no extra scheduler. Notifications are deduplicated and rechecked against current permissions on read. When a source no longer meets a reminder condition, the reminder's resolution event explains why; this does not certify compliance or settle an invoice.

Added capabilities: `asset.manage`, `inspection.complete`, `rams.review`, `rams.publish`, `policy.publish`. Existing policy, COSHH, RAMS, compliance-reporting, restricted-record, premises and Fleet capabilities remain enforced server-side. Administrators retain full access. Existing custom access levels are not silently expanded: explicitly grant the new capabilities to the intended reviewers, publishers and inspectors.

## Database and deployment

Migrations:

1. `20260925010000_compliance_studio`: backfills unique asset QR identifiers; adds optional asset metadata, inspection evidence and corrective-action evidence/verification fields; adds Changes requested to the controlled workflow.
2. `20260925020000_compliance_document_owner`: adds an optional document owner.

No existing records are deleted. New historical fields are nullable or have compatible defaults. The existing deployment script backs up MariaDB, applies migrations and builds/restarts the application. Apply migrations before serving V1.14.0. Both migrations were applied successfully to the disposable local validation database.

Rollback: retain the additive columns and evidence when rolling application code back. Before using an older Prisma client, handle any CHANGES_REQUESTED records explicitly (an audited return to DRAFT is the compatible workflow state). Never drop columns containing newly recorded evidence or receipts. Restore a database backup only as a coordinated recovery, not as routine rollback after users have entered new records.

## Operational boundaries

The hub reports recorded work, not a legal compliance certification. Managers must populate and approve the currently empty policy/RAMS/COSHH libraries, choose appropriate staff groups and set real review/inspection intervals. Evidence can use uploaded controlled documents or authorised HTTPS links; links still need human review for relevance. No automatic approval or external regulatory submission is introduced. Existing Fleet and RIDDOR functionality is reused rather than rebuilt.

Main implementation groups: safety hub/components; controlled-document and RAMS services/routes; staff controlled library and own task views; asset QR/inspection routes; shared task ownership/evidence/edit APIs; live Clive queries; source reminder reconciliation; Fleet archive controls; schema/migrations and regression tests.

Repeatable integration checks are in `scripts/validate-safety-workflows.cjs` and `scripts/validate-staff-compliance.cjs`. They refuse non-local/non-validation databases, require an existing Synthetic reviewer fixture and local server on port 3318, and accept `PLAYWRIGHT_MODULE` for the browser runtime. They deliberately leave their synthetic audit fixtures in that disposable database.

The V1.14.0 production build passed. Live deployment/runtime configuration was not changed by this work. The local production runtime correctly refused insecure development configuration; browser verification uses the local development server. Fleet smoke verification also confirms that historical vehicles cannot be permanently deleted and restoration keeps them out of service.
