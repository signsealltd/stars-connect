# V1.15.0 — Custom Invoice

Previous version: V1.14.0. This feature release adds Custom Invoice as the second choice on the existing Billing page, replacing Enter totals myself. Use agreed amounts retains the funded-day workflow.

Choose one client, confirm the invoice period and payment dates, and add or remove lines. Each line supports a custom description, optional service date/date range, quantity, rate and VAT. Blank service dates use the invoice period. Quantity 1 provides a simple fixed charge. Totals are calculated from rounded line amounts and VAT, then explicitly reviewed before issue.

Payer details and PO/reference are read-only. The issuing service reads the saved billing profile and ignores browser-supplied payer values. A changed billing profile requires a refresh and new review. Clients without saved billing details are shown with a link to Billing setup; this feature does not create or change payer profiles. Supplier/payment information uses existing billing settings.

Custom invoices use the existing invoice sequence, PDF documents, archive, download and payment tracking. They are additional invoices and do not supersede regular invoices. Regular funded billing excludes custom invoices when finding invoices to replace. Request keys prevent retries issuing duplicate invoices; totals, line snapshots and issuance audit records are retained. Long descriptions and service dates wrap onto continuation rows in the PDF instead of being truncated.

Permissions: viewing clients requires Billing review; issuing requires Billing approval and Billing edit. Existing origin checks and authenticated document access apply. No schema migration is required. No production data was modified during testing. Issuing does not email invoices. Draft edits remain in the current browser page; a leave warning protects unsaved work but drafts are not saved across refreshes.

Validation: unit/regression suite, production build, and local browser/API checks covering line persistence, totals, issuance audit, retry idempotency, additional invoices without changed prior statuses, read-only payer enforcement, validation and unauthenticated denial. Desktop/tablet/mobile builder and review screens were checked using synthetic local data.
